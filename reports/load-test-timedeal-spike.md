# 부하 테스트 리포트 — 타임딜 오픈 스파이크 (재고 100 / 요청 2,000)

> **실행 일자:** 2026-08-18 (구성별 3회, 아래 수치는 중앙값)
> **스크립트:** `scripts/timedeal-realistic.js` · 러너 `scripts/run-timedeal-test.sh`
> **목적:** Redis 1차 필터가 "무관한 요청을 지킨다"는 주장을 대조군과 함께 검증

---

## 1. 왜 이 파라미터인가

이전 측정(5만 VU)은 숫자를 키운 것 외에 근거가 없었다. 이번에는 세 가지를 도메인에서 가져왔다.

| 파라미터 | 값 | 근거 |
|---|---|---|
| 초과청약 배수 | 20 : 1 (재고 100 / 요청 2,000) | 이 설계가 존재하는 이유가 이 비율이다. 확정 실패가 통과보다 압도적으로 많아야 앞단 거부가 값을 한다 |
| 도착 형태 | `ramping-arrival-rate`, 피크 700 rps, 4초 | 타임딜은 "2,000명이 앉아 있는" 게 아니라 오픈 순간 요청이 쏟아지는 것이다. VU 기반은 k6 클라이언트가 먼저 병목이 된다 |
| 경쟁 트래픽 | 상품 조회 50 rps, 전 구간 25초 | 주장이 "무관한 요청이 밀린다"이므로 밀려나는 쪽을 같이 재야 한다 |

측정 환경: Apple M2 Max / 32GB / macOS. Spring Boot 4, JDK 21 Virtual Thread, HikariCP `maximum-pool-size=20`, PostgreSQL 16(Docker), Redis 7(Docker). k6 v1.7.1 단일 머신.

## 2. 두 가지 구성

| | A — 기본 | B — 대조군 |
|---|---|---|
| Redis 1차 필터 | 동작 | 무력화 (재고 키를 `99999999` 로 덮어 항상 통과) |
| 거부 주체 | Redis Lua | DB Optimistic Lock |
| 코드 변경 | 없음 | 없음 |

B 는 "Redis 없이 같은 부하를 DB 가 받으면?" 을 코드 수정 없이 만드는 방법이다. DB 재고는 양쪽 100 이라 성공 건수가 같아야 하고, 실제로 같았다.

---

## 3. 정합성 — 양쪽 동일

```
                 A(기본)   B(대조군)
구매 성공            100        100      재고와 정확히 일치
Oversell            없음       없음
409 품절           1,999          0
409 버전충돌            0      1,999
5xx                   0          0
DB remaining          0          0
DB version          100        100
```

**5xx 0건.** 5만 VU 런에서는 k6 체크가 `201·409·500` 을 한 덩어리로 세는 바람에 답할 수 없던 질문인데, 이번 스크립트는 상태별로 분리해서 센다.

**그리고 실패의 성격이 정반대로 갈린다.** 같은 부하에 같은 결과(성공 100)인데, 필터가 있으면 전부 품절이고 없으면 전부 버전 충돌이다. Redis 가 재고 없음을 즉시 판정하느냐, DB 까지 가서 경합하다 재시도를 소진하느냐의 차이다.

이 구분은 처음부터 보이던 게 아니다. 개선 전에는 두 경우 모두 `STOCK_EXHAUSTED` 로 나가서 4,000 건이 전부 "품절" 로 집계됐다(§6-2).

---

## 4. 결과 — 밀려나는 쪽 (상품 조회 p95)

이 측정의 주 지표다.

| 구간 | A (기본) | B (대조군) |
|---|---:|---:|
| 스파이크 전 | 6.29 ms | 5.88 ms |
| **스파이크 중** | **5.32 ms** | **4.43 ms** |
| 스파이크 후 | 5.77 ms | 6.01 ms |

**양쪽 모두 조회 지연이 안 늘었다.** Redis 를 꺼도 마찬가지였다.

이 시스템의 주장 — "확정 실패 요청이 커넥션을 붙들어 무관한 요청을 밀어낸다" — 은 **이 규모에서 재현되지 않았다.**

이유는 산수로 나온다. 700 rps × 평균 7ms = 약 5개의 동시 커넥션이다. 풀은 20개다. 경합이 일어날 수가 없다. 부하가 부족한 것이지 설계가 증명된 게 아니다.

## 5. 결과 — 구매 경로 자체

조회는 안 밀렸지만 구매 경로의 비용은 확실히 갈렸다.

| p95 (3회) | A (기본) | B (대조군) |
|---|---:|---:|
| 1회 | 3.33 ms | 10.37 ms |
| 2회 | 3.24 ms | 8.32 ms |
| 3회 | 2.73 ms | 9.61 ms |
| **중앙값** | **3.24 ms** | **9.61 ms** |

**약 3배.** 구성별 편차는 작고 두 구성은 겹치지 않는다.

### 5-1. DB 왕복 횟수

`pg_stat_user_tables` 의 `time_deals` 스캔 수를 요청 수로 나눈 값이다.

| | A (기본) | B (대조군) |
|---|---:|---:|
| time_deals 스캔 | 2,420 | 14,422 |
| 요청당 | **1.15회** | **6.9회** |

약 6배다. 내역은 이렇게 설명된다.

```
A: findById 2,099 + findCurrentVersion 100 + UPDATE 100          ≈ 2,300
B: findById 2,099
   + 실패 1,999건 × (findCurrentVersion 3 + UPDATE 3)            = 11,994
   + 성공 100건 × (findCurrentVersion 1 + UPDATE 1)              =    200
                                                                 ≈ 14,293
```

**재시도 3회가 실패 경로에서 DB 왕복을 6배로 만든다.** 자원을 아끼려고 만든 재시도가 경합 상황에서는 자원을 더 쓴다.

### 5-2. Redis 명령 통계

| 명령 | A (기본) | B (대조군) |
|---|---:|---:|
| `evalsha` | 2,100 (7.90µs) | 2,099 (10.14µs) |
| `decrby` | 100 | 2,099 |
| `incrby` | **0** | **1,999** |

`INCRBY` 는 롤백 경로에서만 호출되므로 이 값이 곧 버전 충돌 횟수다. 다만 이제는 응답의 `STOCK_VERSION_CONFLICT` 코드로 직접 셀 수 있고, 두 값이 정확히 일치하는 것으로 교차 확인했다.

- A: 0건. Redis 가 1,999건을 미리 걸러서 DB 에 도달한 100건이 서로 경합하지 않았다.
- B: 1,999건. 전부 재시도 3회를 소진하고 실패했다.

**A 구성에서는 Optimistic Lock 재시도 경로가 한 번도 밟히지 않는다.** 이 시나리오로는 "재시도 3회가 적절한가"에 답할 수 없다.

## 6. 측정하면서 드러난 결함

부하 자체와 별개로, 돌리는 과정에서 나온 것들이다. 앞의 둘은 이번에 고쳤다.

### 6-1. `SCHEDULED → ACTIVE` 전이 경로가 없었다 — 수정함

`TimeDeal.create()` 는 항상 `SCHEDULED` 로 만드는데 `ACTIVE` 로 바꾸는 코드가 리포지토리 어디에도 없었다. `isActiveAt()` 이 `status == ACTIVE` 를 요구하니 **API 로 만든 딜은 전부 `400 TIME_DEAL_NOT_ACTIVE`** 였다. 첫 측정 시도에서 구매 2,099 건이 통째로 실패한 원인이 이거였고, 이전 측정들도 SQL 로 상태를 직접 올려서 돌렸을 것이다.

고칠 때 선택지가 둘이었다.

| | 전이 스케줄러만 추가 | 판단 주체를 시간으로 |
|---|---|---|
| 오픈 직후 | 스케줄러 주기만큼 못 산다 | 즉시 열린다 |
| 상태 라벨 | 정확 | 잠깐 늦을 수 있다 |
| 스케줄러 장애 시 | 판매가 안 열린다 | 판매는 열린다 |

**시간을 판단 주체로 뒀다.** 스케줄러 주기만큼 생기는 창이 하필 타임딜에서 가장 중요한 순간 — 오픈 직후 — 과 정확히 겹치기 때문이다.

```kotlin
fun isActiveAt(now: Instant): Boolean =
    now in startAt..endAt &&
        status != TimeDealStatus.SOLD_OUT &&
        status != TimeDealStatus.ENDED
```

상태 라벨은 `TimeDealStatusScheduler`(5초 주기)가 따라간다. 라벨이 필요한 이유는 판매 판단이 아니라 운영 가시성과 `findAllActive()` 같은 상태 기준 조회다. 판단과 라벨을 분리했으니 잡이 죽어도 판매는 열린다.

검증: 딜 생성 직후 상태가 `SCHEDULED` 인 상태에서 재고 2 짜리 딜에 구매 3건을 보내 2건 성공·3번째 `STOCK_EXHAUSTED` 를 확인했고, 5초 뒤 라벨이 `ACTIVE` 로 바뀌는 것을 확인했다. 측정 러너에서도 SQL 개입 단계를 제거했다.

### 6-2. 버전 충돌이 "품절" 로 나갔다 — 수정함

```kotlin
// before
StockDecreaser.Result.VersionConflict -> {
    throw StockExhaustedException()
}
```

재고가 남아 있는데 `409 STOCK_EXHAUSTED` 가 응답됐다. 그 예외의 주석은 "클라이언트는 409 를 보면 재시도해도 의미 없음을 알 수 있다" 인데, 버전 충돌은 재시도하면 성공할 수 있는 실패다. 정반대 신호를 주고 있었다.

`StockVersionConflictException`(`STOCK_VERSION_CONFLICT`, 409)으로 분리하고, `Result.VersionConflict(attempts)` 가 시도 횟수를 실어 보내게 했다. HTTP 상태는 409 를 유지했다 — 상태 충돌인 건 같고, 409 를 종료 상태로 취급하는 기존 클라이언트를 깨뜨리지 않기 위해서다. 재시도 가능 여부는 `errorCode` 로 구분한다.

효과는 §3 의 표에 그대로 나온다. 개선 전이라면 A·B 두 구성의 4,000 건이 전부 "품절" 한 칸에 들어갔다.

### 6-3. Redis 앞에서 이미 DB 를 두 번 친다 — 미수정

`PurchaseTimeDealUseCase` 는 Redis 를 부르기 전에 `findById` 와 `getPurchasedQuantity` 를 실행한다. A 구성의 `time_deals` 스캔 2,420 이 그 증거다 — 요청 2,100 건이 전부 DB 를 읽었다.

**Redis 1차 필터가 막는 것은 재고 차감 UPDATE 지 DB 접근 자체가 아니다.** `StockDecreaser` 주석의 "실패 시 DB 에 접근하지 않음" 은 정확하지 않다.

고치려면 딜 메타데이터를 캐시에 올려 `findById` 를 걷어내야 하는데, 그러면 캐시 무효화라는 새 문제가 생긴다. 지금 부하에서 이 두 SELECT 가 병목이라는 근거가 없어서 그대로 뒀다.

### 6-4. 테이블이 작아서 쿼리 계획이 프로덕션과 다르다 — 미수정

`time_deals` 4행, `time_deal_purchases` 200행 상태에서 PostgreSQL 은 인덱스를 무시하고 순차 스캔을 골랐다(B 구성 `seq_scan` 14,421 / `idx_scan` 1). 인덱스는 정의돼 있고 `EXPLAIN` 을 따로 돌리면 정상적으로 탄다(0.18ms, 유니크 인덱스 사용).

**이 부하 테스트는 인덱스 설계를 검증하지 못한다.** 실제 규모의 데이터를 채우지 않으면 플래너가 프로덕션과 다른 선택을 한다.

## 7. 이 측정으로 답한 것과 못 답한 것

답한 것:

- 재고 100 / 요청 2,000 / 20:1 에서 Oversell 은 나지 않는다. Redis 유무와 무관하다
- 5xx 는 0건이다
- Redis 1차 필터는 구매 경로 p95 를 약 3배(9.61ms → 3.24ms), DB 왕복을 약 6배(6.9회 → 1.15회) 줄인다
- 실패의 성격이 구성에 따라 갈린다 — 필터가 있으면 품절, 없으면 버전 충돌. 정상 구성에서 재시도 경로는 0회 밟힌다

못 답한 것:

- **"무관한 요청을 지킨다"는 여전히 확인되지 않았다.** 조회 p95 가 세 번 다 안 늘었고 필터를 꺼도 마찬가지다. 커넥션 풀이 포화되는 지점까지 올리지 않으면 이 효과는 관측되지 않는다
- 재시도 3회가 적절한 값인지 — 정상 구성에서 이 경로가 안 밟히므로 이 시나리오로는 답이 안 나온다
- 인덱스 설계의 타당성 — 데이터가 작아 플래너가 다른 선택을 했다

## 8. 다음

풀 포화 지점을 찾는 게 남았다. 요청률을 올려 가며 조회 p95 가 꺾이는 지점을 찾으면, 그 지점이 이 설계가 값을 하기 시작하는 경계고 "왜 이 숫자냐" 에 답이 되는 유일한 수치다.

측정 전 조건이던 두 결함(§6-1, §6-2)은 고쳤으니, 이제 API 만으로 재현되고 실패 사유도 응답에서 바로 구분된다.
