# 부하 테스트 리포트 — 타임딜 오픈 스파이크

> **실행 일자:** 2026-08-18
> **스크립트:** `scripts/timedeal-realistic.js` · 러너 `scripts/run-timedeal-test.sh` · 풀 스윕 `scripts/pool-sweep.sh`
> **목적:** "Redis 1차 필터가 DB 도달 전에 확정 실패를 걷어낸다" 는 설계 의도가 실제로 지켜지는지 확인하고, 그 효과의 메커니즘과 경계를 찾는다

---

## 1. 왜 이 파라미터인가

이전 측정은 숫자를 키운 것 외에 근거가 없었다. 이번에는 세 가지를 도메인에서 가져왔다.

| 파라미터 | 값 | 근거 |
|---|---|---|
| 초과청약 배수 | 재고 100 대비 요청 6,000 (60:1) | 확정 실패가 통과보다 압도적으로 많아야 앞단 거부가 값을 한다. 이 비율이 설계의 전제다 |
| 도착 형태 | `ramping-arrival-rate`, 피크 1,500 rps 를 3초 유지 | 타임딜은 "N 명이 앉아 있는" 게 아니라 오픈 순간 요청이 쏟아지는 것이다. VU 기반은 클라이언트가 먼저 병목이 된다 |
| 경쟁 트래픽 | 상품 조회 50 rps, 전 구간 | 주장이 "무관한 요청이 밀린다" 이므로 밀려나는 쪽을 같이 재야 한다 |

환경: Apple M2 Max / 32GB. Spring Boot 4, JDK 21 Virtual Thread, PostgreSQL 16(Docker), Redis 7(Docker), k6 v1.7.1. **k6 와 대상이 같은 머신에서 돈다.**

### 측정 절차에서 통제한 것

- **런 전 데이터 초기화** (`TRUNCATE` + `FLUSHDB`) — 딜·구매 행이 쌓이면 조회 비용이 달라져 런끼리 비교가 안 된다
- **두 구성을 번갈아 실행** — 머신 상태가 시간에 따라 변하므로 한쪽을 몰아 돌리면 그 드리프트가 구성 차이로 오독된다
- **워밍업 런 폐기** — 직전 부하가 무거우면 첫 런이 그 여파를 받는다

## 2. 세 가지 구성

| | A — 필터 OFF | B — 필터 ON (순서 이전) | C — 필터 ON (순서 수정) |
|---|---|---|---|
| Redis 1차 필터 | 무력화 (재고 키를 크게 덮음) | 동작 | 동작 |
| 호출 순서 | `findById` → `getPurchasedQuantity` → Redis | 동일 | **Redis → `findById`** |
| 거부 주체 | DB Optimistic Lock | Redis Lua (단, DB 조회 이후) | Redis Lua |

A 는 코드를 고치지 않고 만든 대조군이다. Redis 재고 키를 `99999999` 로 덮으면 Lua 가 항상 통과시켜 DB 가 유일한 거부 주체가 된다.

## 3. 정합성 — 전 구성 동일

모든 구성, 모든 풀 크기에서 같았다.

```
구매 성공        100        재고와 정확히 일치
Oversell         없음
5xx                0
DB remaining       0
```

정합성은 이 실험의 어떤 변수에도 흔들리지 않았다. 아래 모든 논의는 정합성이 아니라 자원에 관한 것이다.

## 4. 설계 의도가 지켜지고 있었나 — 아니었다

`StockDecreaser` 에는 처음부터 이렇게 적혀 있었다.

```kotlin
// 실패 시 DB 에 접근하지 않음 -> DB 부하 차단이 핵심 목적
// Redis 를 통과했으므로 "유력 후보" 만 DB 에 도달한다.
```

측정해보니 지켜지지 않았다.

| 1,500 rps · 요청 약 6,000건 | A (필터 OFF) | B (순서 이전) | C (순서 수정) |
|---|---:|---:|---:|
| `time_deals` 스캔 / 요청 | 6.13 ~ 7.58 | 1.02 | **0.08 ~ 0.11** |
| `time_deal_purchases` 스캔 / 요청 | 0.02 | 0.99 | **0.02** |
| **합계** | **~6.8회** | **2.01회** | **0.11회** |

B 에서는 요청 5,999건이 전부 DB 를 두 번씩 쳤다. 재고 소진으로 거부될 5,899건도 예외 없이.

### 왜 그랬나

주석은 `StockDecreaser` **안에서만** 참이었다. `decrease()` 내부에서는 Redis 실패 시 정말로 DB 를 안 친다. 그런데 그 함수가 불리기 전에 `PurchaseTimeDealUseCase` 가 이미 두 번 조회했다.

```
① findById                    ← DB
② validator.check             ← 순수
③ getPurchasedQuantity        ← DB
④ stockDecreaser.decrease     ← 여기서 처음 Redis
```

파일 하나만 읽으면 맞고, 흐름 전체를 보면 틀린 상태였다.

### 어떻게 고쳤나

Redis 재고 확인을 맨 앞으로 옮기고, `getPurchasedQuantity` 선검사를 제거했다.

```
① Redis 재고 확인 (GET)        ← 확정 실패는 여기서 끝. DB 접근 0
② findById + 검증
③ Redis Lua 차감 + DB OL
④ UPSERT WHERE quantity + ? <= maxPerUser
```

**①은 차감이 아니라 확인이다.** 실패해도 되돌릴 것이 없어 롤백 경로가 늘지 않는다. 원자적 판정은 여전히 ③의 Lua 가 한다 — ①을 통과하고 ③에서 실패하는 요청이 존재하지만, 그건 결함이 아니라 필터의 성격이다.

③의 선검사 제거는 정확성에 영향이 없다. ④의 UPSERT 가 `WHERE quantity + ? <= maxPerUser` 로 한도를 원자적으로 보장하고 있었다. 선검사는 재구매자 한 명의 Redis 차감+롤백을 아끼려고 **모든 요청**이 DB 를 한 번 더 치는 거래였다.

같은 사용자가 동시에 20회 시도해도 정확히 1건만 성공하고 Redis·DB 재고가 일치하는 것을 통합 테스트로 확인했다.

### 결과

| | B (순서 이전) | C (순서 수정) |
|---|---:|---:|
| DB 왕복 / 요청 | 2.01회 | **0.11회** |
| 구매 p95 | 10.62 ms | **0.89 ~ 0.98 ms** |

**DB 왕복 18배, 구매 응답 11배.** 요청 5,999건 중 DB 까지 온 것은 500~680건이다.

재고 100 에 대해 500~680 이 온 이유는 재고가 마르는 동안 도착한 요청들이 확인을 통과하기 때문이다. 애초 기대는 "재고 × 1.1" 이었으니 그보다는 크지만, 요청 수 기준으로는 **9%** 다.

## 5. 밀려나는 쪽 — 상품 조회 p95

값은 스파이크 중 p95(ms), 괄호는 스파이크 전 대비 배수.

| 피크 | 필터 ON | 필터 OFF |
|---:|---|---|
| 700 rps | 2.02 · 2.74 · 2.98 | 2.71 · 2.83 · 10.95 |
| **1,500 rps** | **2.4 ~ 3.2** | **131 ~ 191** |
| 3,000 rps | 편차 66 ~ 1,354 (측정 불가) | 1,613 ~ 2,122 |

**700 rps 는 경계 아래다.** 두 구성이 사실상 같다. 거부될 요청이 풀을 경합시킬 만큼 많지 않다.

**1,500 rps 에서 갈린다.** 약 60배.

**3,000 rps 는 측정 범위 밖이다.** 양쪽 다 무너지고 필터 ON 의 편차가 20배에 달한다. 한 런에서는 12,000 요청 중 7,520 건만 완료됐다. k6 와 애플리케이션이 CPU 를 나눠 쓰는 단일 머신의 한계이므로 **이 구간 숫자로는 결론을 내지 않는다.**

경계는 **700 ~ 1,500 rps 사이**다. `http_req_blocked` 가 이 구간 전체에서 0.01ms 였으므로 측정기 병목이 아니다.

## 6. 메커니즘 확정 — 커넥션 풀 스윕

"커넥션 풀을 지킨다" 는 여기까지 정황이었다. 조회가 느려진 것은 봤지만 풀이 마르는 것은 보지 않았다.

HikariCP 풀 크기를 바꿔 가며 1,500 rps 를 고정하고, 스파이크 동안 `hikaricp.connections.active` 와 `pending` 을 200ms 간격으로 샘플링했다.

| 풀 | | 조회 p95 | active 최대 | **pending 최대** | 충돌 |
|---:|---|---:|---:|---:|---:|
| **10** | ON | 2.10 · 2.50 | 1 / 10 | **0** | 0 |
| | OFF | 869.50 · 867.83 | 10 / 10 | **930 · 977** | 4,978 · 4,970 |
| **20** | ON | 2.65 · 2.38 | 7 / 20 | **0** | 0 |
| | OFF | 322.85 · 198.64 | 20 / 20 | **370 · 255** | 5,574 · 5,795 |
| **40** | ON | 2.43 · 2.76 | 3 / 40 | **0** | 0 |
| | OFF | 99.16 · 181.28 | 40 / 40 | **114 · 267** | 5,899 · 5,785 |

### 6-1. 병목은 커넥션 풀이 맞다

대조군은 **모든 풀 크기에서 100% 포화**되고 대기열이 최대 930까지 쌓인다. 필터 ON 은 **어느 크기에서도 마르지 않는다** — 최대 7개를 썼다.

추론이 아니라 관측이다.

### 6-2. 풀만 늘리는 것으로는 안 된다

풀을 10에서 40으로 4배 늘리자 대조군 조회 p95 가 869ms → 140ms 로 약 6배 개선됐다. **완화는 된다.**

그런데 같은 조건에서 필터 ON 은 2.4ms 다. **4배 늘린 풀이 여전히 60배 느리다.**

그리고 풀은 공짜가 아니다. PostgreSQL 은 커넥션마다 백엔드 프로세스를 띄우고, 그 비용은 인스턴스 수만큼 곱해진다.

### 6-3. 재시도가 자기 증폭한다

풀이 커질수록 충돌이 늘었다.

```
pool 10 → 4,978 · 4,970
pool 20 → 5,574 · 5,795
pool 40 → 5,899 · 5,785      ← 사실상 전량
```

커넥션을 더 주면 같은 행을 동시에 때리는 요청이 늘고, 충돌이 늘면 재시도가 늘고, 재시도가 늘면 왕복이 는다. 풀 확대가 선형으로 먹히지 않는 이유가 이것이다 — 늘린 자원의 일부가 경합 증폭으로 되돌아온다.

## 7. 측정하면서 드러난 결함

### 7-1. `SCHEDULED → ACTIVE` 전이 경로가 없었다 — 수정함

`TimeDeal.create()` 는 항상 `SCHEDULED` 로 만드는데 `ACTIVE` 로 바꾸는 코드가 없었다. `isActiveAt()` 이 `status == ACTIVE` 를 요구하니 **API 로 만든 딜은 전부 `400`** 이었다. 첫 측정에서 구매 2,099 건이 통째로 실패한 원인이고, 이전 측정들은 SQL 로 상태를 올려서 돌렸다.

**테스트 27건이 통과하는 상태였다.** 단위 테스트는 물어본 것만 답한다.

선택지가 둘이었다.

| | A. 전이 워커만 추가 | B. 판단 주체를 시간으로 |
|---|---|---|
| 오픈 직후 | 워커 주기만큼 못 산다 | 즉시 열린다 |
| 상태 라벨 | 정확 | 잠깐 늦다 |
| 워커 장애 시 | 판매가 안 열린다 | 판매는 열린다 |

**B 를 택했다.** A 의 지연 창이 하필 타임딜에서 가장 중요한 순간과 겹친다. 라벨은 `TimeDealStatusScheduler`(5초)가 뒤따라간다. 대가는 `status` 컬럼이 최대 5초 동안 진실이 아니라는 것이다.

측정 러너에서 `UPDATE time_deals SET status='ACTIVE'` 를 제거했고 그대로 돈다.

### 7-2. 버전 충돌이 "품절" 로 나갔다 — 수정함

```kotlin
// before
StockDecreaser.Result.VersionConflict -> throw StockExhaustedException()
```

재고가 남아 있는데 `409 STOCK_EXHAUSTED` 가 응답됐다. 그 예외의 주석은 "클라이언트는 409 를 보면 재시도해도 의미 없음을 알 수 있다" 인데, 버전 충돌은 재시도하면 성공할 수 있는 실패다.

`StockVersionConflictException`(`STOCK_VERSION_CONFLICT`, 409)으로 분리하고 `Result.VersionConflict(attempts)` 가 시도 횟수를 싣게 했다.

실패를 예외로 던지지 않고 `sealed class Result` 로 돌려주는 이유가 여기 있다. 예외는 호출자가 `catch (e: Exception)` 한 줄로 뭉갤 수 있고, 실패 케이스를 추가해도 컴파일러가 알려주지 않는다. 값으로 돌려주면 `when` 이 분기 누락을 컴파일 타임에 막는다 — Go 에서 `error` 를 반환값으로 다루는 것과 같은 방향이다.

그래서 결과마다 다른 응답을 빠뜨릴 수 없다.

| Result | 응답 | 클라이언트가 할 일 |
|---|---|---|
| `Success` | `201` | — |
| `StockExhausted` | `409 STOCK_EXHAUSTED` | 재시도해도 의미 없음 |
| `VersionConflict(attempts)` | `409 STOCK_VERSION_CONFLICT` | 재시도하면 성공할 수 있음 |

HTTP 상태를 둘 다 409 로 유지한 건 상태 충돌인 건 같고, 409 를 종료 상태로 취급하는 기존 클라이언트를 깨뜨리지 않기 위해서다.

분리 전에는 §6 의 충돌 열을 만들 수 없었다. 충돌 횟수를 알려면 Redis `INCRBY` 호출 수를 세는 우회로가 필요했고, 지금은 응답으로 집계되며 `INCRBY` 값과 교차 확인된다.

### 7-3. 남은 것

- Redis 앞에서 `findById` 를 한 번 친다. DB 도달 0.11회 중 대부분이 이것이다. 없애려면 딜 메타데이터를 캐시에 올려야 하는데 무효화 문제가 생긴다
- 테이블이 작아 쿼리 계획이 프로덕션과 다르다. 이 부하로는 인덱스 설계가 검증되지 않는다

## 8. 답한 것과 못 답한 것

답한 것:

- 정합성은 구성·풀 크기와 무관하다. Oversell 0, 5xx 0
- 설계 의도(DB 도달 전 차단)가 지켜지지 않고 있었고, 순서를 바꿔 달성했다. DB 왕복 2.01 → 0.11회
- **병목은 커넥션 풀이다.** 대조군은 모든 풀 크기에서 100% 포화되고 대기열이 930까지 쌓인다. 필터 ON 은 최대 7개를 쓴다
- **풀만 늘려서는 해결되지 않는다.** 4배 늘려 6배 개선되지만 여전히 60배 느리고, 충돌이 4,978 → 5,899 로 늘어난다
- 효과가 나타나는 경계는 700~1,500 rps 사이다

못 답한 것:

- **필터 ON 의 한계.** 어느 풀 크기에서도 마르지 않아 ON 쪽 경계는 못 찾았다. "안 무너진다" 가 아니라 **"이 규모에서는 안 무너진다"** 까지가 지금 말할 수 있는 전부다
- **재시도 3회가 적절한지.** 정상 구성에서 관측된 충돌은 1,500 rps 에서 2건뿐이라 표본이 부족하다
- **경계의 정확한 위치.** 700~1,500 사이를 촘촘히 훑지 않았다
- 3,000 rps 이상의 거동 — 측정 환경이 먼저 무너진다
