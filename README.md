# ecommerce-server — 타임딜 재고 차감

> 확정 실패할 요청을 앞단에서 버려 DB 커넥션 풀을 지키는 재고 차감 파이프라인.

Kotlin 2.2 / JDK 21 (Virtual Thread) / Spring Boot 4 / jOOQ 3.19 / PostgreSQL 16 / Redis 7 / k6

---

## 무엇을 지키려고 만들었나

재고 100에 동시 2,000이 들어오면 1,900건은 확정 실패다. 재고를 열기도 전에 이미 정해져 있는 숫자다.

처음엔 이걸 "Oversell 을 어떻게 막느냐" 문제로 봤다. 그런데 그건 `UPDATE ... WHERE stock > 0` 한 줄로도 막힌다. 재고가 음수가 되는 일은 안 생긴다.

진짜 걸리는 건 다른 데 있다. 그 1,900건이 "너 실패야"라는 말을 듣기까지 커넥션을 하나씩 붙들고 있다. 풀은 20개다. 그동안 상품 조회도, 주문 내역도, 타임딜과 아무 상관 없는 요청까지 같은 줄에 선다. 타임딜 하나가 서비스 전체를 느리게 만든다.

그래서 이건 방어선을 쌓는 문제가 아니라 **어차피 실패할 요청에 얼마나 비싼 자원을 쓰느냐**의 문제다. 답은 층을 늘리는 게 아니라, 거부 비용이 싼 곳에서 먼저 거부하는 것이다.

## 파이프라인

```
요청 ──→ [0차] Redis 재고 확인 (GET)          거부 비용: 메모리 읽기
           │ 재고 없음 → 409, DB 접근 0
           ▼
         [1차] 딜 조회 + 활성 검증              여기부터 DB
           ▼
         [2차] Redis Lua 원자 차감              원자적 판정
           │ 재고 부족 → 409
           ▼
         [3차] DB Optimistic Lock UPDATE
           │ version 불일치 → Redis 복구 + 409 (최대 3회 재시도)
           ▼
         [4차] UPSERT WHERE quantity + ? <= maxPerUser
           │ 1인 한도 초과 → Redis 복구 + 409
           ▼
         구매 확정
```

순서를 정한 기준은 하나다. **싼 거부를 앞에.**

0차는 차감이 아니라 확인이다. 실패해도 되돌릴 게 없어서 롤백 경로가 늘지 않는다. 원자적 판정은 2차의 Lua 가 하고, 0차를 통과했다가 2차에서 실패하는 요청이 존재한다 — 그건 결함이 아니라 필터의 성격이다. 0차는 게이트가 아니라 **명백히 안 될 요청을 싸게 걷어내는 자리**다.

세 층이 정합성을 겹쳐서 보장하는 구조가 아니다. **각 층이 서로 다른 실패를 맡는다.**

| 층 | 막는 것 | 이게 없으면 |
|---|---|---|
| Redis Lua | 재고 소진 | 확정 실패가 DB 까지 온다 |
| DB OL | **Redis 와 DB 의 불일치** | Redis 가 재시작되면 초과 판매된다 |
| UPSERT WHERE | 1인 한도 | 한 사람이 여러 번 산다 |

특히 2층이 핵심이다. Redis 는 휘발성이고 DB 와 어긋날 수 있어서, Redis 만 믿으면 재시작 한 번에 Oversell 이 난다. **DB OL 은 Redis 가 틀렸을 때의 최종 진실이다.**

## 의도대로 동작하는지 재봤더니 아니었다

전문은 [`reports/load-test-timedeal-spike.md`](reports/load-test-timedeal-spike.md).

`StockDecreaser` 에는 처음부터 이렇게 적혀 있었다.

```kotlin
// 실패 시 DB 에 접근하지 않음 -> DB 부하 차단히 핵심 목적
// Redis 를 통과했으므로 "유력 후보" 만 DB 에 도달한다.
```

재고 100 에 6,000 요청을 넣고 `pg_stat_user_tables` 를 봤다.

```
time_deals           스캔 6,115   →  요청당 1.02회
time_deal_purchases  스캔 5,950   →  요청당 0.99회
```

**요청 5,999건이 전부 DB 를 두 번씩 쳤다.** 재고 소진으로 거부될 5,899건도 예외 없이.

### 주석은 맞았는데 흐름이 틀렸다

`decrease()` 안에서는 진짜로 Redis 실패 시 DB 를 안 친다. 그런데 그 함수가 불리기 **전에** 유스케이스가 이미 두 번 조회하고 있었다.

```
① findById               ← DB
② validator.check
③ getPurchasedQuantity   ← DB
④ decrease()             ← 여기서 처음 Redis
```

**파일 하나만 읽으면 맞고, 흐름 전체를 보면 틀린 상태였다.** 의도를 주석으로 남겨뒀기 때문에 어긋난 걸 찾을 수 있었다.

### 두 가지를 고쳤다

**Redis 확인을 맨 앞으로.** 차감이 아니라 `GET` 이라 실패해도 되돌릴 게 없다.

**`getPurchasedQuantity` 선검사 제거.** ④의 UPSERT 가 `WHERE quantity + ? <= maxPerUser` 로 이미 한도를 원자적으로 보장하고 있었다. 선검사는 재구매자 한 명의 롤백을 아끼려고 **모든 요청**이 DB 를 한 번 더 치는 거래였다. 같은 사용자가 동시에 20회 시도해도 1건만 성공하는 것을 테스트로 확인했다.

| | 필터 OFF | 순서 이전 | **순서 수정** |
|---|---:|---:|---:|
| DB 왕복 / 요청 | ~6.8회 | 2.01회 | **0.11회** |
| 구매 p95 | 144~203 ms | 10.62 ms | **0.89~0.98 ms** |

**DB 왕복 18배, 구매 응답 11배.** 요청 6,000건 중 DB 까지 온 것은 500~680건이다.

## 그래서 무엇이 지켜졌나 — 커넥션 풀

조회가 느려진 건 봤지만 풀이 마르는 건 안 봤었다. 풀 크기를 바꿔 가며 `hikaricp.connections.pending` 을 직접 샘플링했다. 1,500 rps 고정.

| 풀 | | 조회 p95 | active 최대 | **pending 최대** | 충돌 |
|---:|---|---:|---:|---:|---:|
| **10** | ON | 2.1 ms | 1 / 10 | **0** | 0 |
| | OFF | 869 ms | 10 / 10 | **930** | 4,978 |
| **20** | ON | 2.7 ms | 7 / 20 | **0** | 0 |
| | OFF | 323 ms | 20 / 20 | **370** | 5,574 |
| **40** | ON | 2.4 ms | 3 / 40 | **0** | 0 |
| | OFF | 140 ms | 40 / 40 | **267** | 5,899 |

**대조군은 모든 풀 크기에서 100% 포화되고 대기열이 930까지 쌓인다. 필터가 있으면 어느 크기에서도 마르지 않는다** — 최대 7개를 썼다.

### 풀만 늘리면 되지 않나

가장 자연스러운 반론이라 재봤다. 10에서 40으로 4배 늘리자 869ms 가 140ms 로 **6배 개선됐다. 완화는 된다.**

그런데 같은 조건에서 필터 ON 은 2.4ms 다. **4배 늘린 풀이 여전히 60배 느리다.** 그리고 PostgreSQL 은 커넥션마다 백엔드 프로세스를 띄우고, 그 비용은 인스턴스 수만큼 곱해진다.

### 그리고 재시도가 자기 증폭한다

```
pool 10 → 충돌 4,978
pool 20 → 충돌 5,574
pool 40 → 충돌 5,899     사실상 전량
```

커넥션을 더 주면 같은 행을 동시에 때리는 요청이 늘고, 충돌이 늘면 재시도가 늘고, 재시도가 늘면 왕복이 는다. **늘린 자원의 일부가 경합 증폭으로 되돌아온다.**

## 언제 값을 하고 언제 안 하나

조회 p95, 스파이크 중 기준.

| 피크 | 필터 ON | 필터 OFF |
|---:|---:|---:|
| 700 rps | 2.0 ~ 3.0 ms | 2.7 ~ 11.0 ms |
| **1,500 rps** | **2.4 ~ 3.2 ms** | **131 ~ 191 ms** |
| 3,000 rps | 편차 20배 | 1,613 ~ 2,122 ms |

**700 rps 아래에서는 두 구성이 사실상 같다.** 거부될 요청이 풀을 경합시킬 만큼 많지 않다. 이 구간에서 Redis 는 이득 없이 "재고의 두 번째 진실" 이라는 비용만 남긴다.

**3,000 rps 는 측정 범위 밖이다.** 양쪽 다 무너지고 필터 ON 의 편차가 20배다. k6 와 애플리케이션이 같은 머신에서 CPU 를 나눠 쓰는 한계이므로 이 구간 숫자로는 결론을 내지 않았다.

정합성은 전 구간에서 유지됐다. 3,000 rps · 필터 OFF 로 12,000 요청을 몰아도 성공은 정확히 100건, 5xx 는 0이다.

## 버전 충돌은 어떻게 처리되나

`decreaseStockWithVersion` 은 `WHERE version = ? AND remaining_stock >= ?` 로 UPDATE 한다. 다른 요청이 먼저 커밋했으면 version 이 어긋나 affected rows 가 0 이 되고, 그게 충돌 신호다.

```kotlin
repeat(MAX_RETRY_COUNT) {                        // 3
    val currentVersion = findCurrentVersion(id)  // 매 회 새로 읽는다
        ?: run { rollback(); return VersionConflict }
    if (decreaseStockWithVersion(id, qty, currentVersion)) return Success
}
rollback()                                        // Redis INCRBY 로 되돌리고
return VersionConflict
```

핵심은 재시도마다 version 을 다시 읽는 것이다. 들고 있던 값으로 다시 쏘면 영원히 실패한다. 3회를 다 쓰면 Redis 차감을 되돌리고 `VersionConflict` 를 돌려준다. 실패를 예외가 아니라 `sealed class Result` 로 표현해서, 호출자가 `when` 으로 사유별 분기를 강제받는다.

측정에서 이 경로는 필터 ON 일 때 **0회** 밟혔다. Redis 가 1,999건을 먼저 걸러서 DB 에 도달한 100건이 서로 경합하지 않았다. 대조군에서는 1,999건 전부가 3회를 소진하고 실패했다. 그러니까 재시도 3회가 적절한 값인지는 아직 모른다. 정상 구성에서는 그 코드가 안 돈다.

### 실패를 품절로 바꿔 보내고 있었다

```kotlin
// before
StockDecreaser.Result.VersionConflict -> {
    throw StockExhaustedException()
}
```

버전 충돌을 품절로 바꿔서 내보냈다. 사용자는 재고가 있는데 `409 STOCK_EXHAUSTED` 를 받는다. 그 예외에 달린 주석은 "클라이언트는 409 를 보면 재시도해도 의미 없음을 알 수 있다" 인데, 버전 충돌은 재시도하면 성공할 수 있는 실패다. 정반대 신호를 주고 있었다.

관측도 같이 막혔다. 로그에도 메트릭에도 둘을 가르는 게 없어서, 첫 측정 때는 Redis `INCRBY` 호출 수를 세는 우회로로 충돌 횟수를 알아내야 했다.

`STOCK_VERSION_CONFLICT` 로 분리하고 `Result.VersionConflict(attempts)` 가 시도 횟수를 싣게 했다. HTTP 상태는 409 를 유지했다 — 상태 충돌인 건 같고, 409 를 종료 상태로 취급하는 기존 클라이언트를 깨뜨리지 않는다. 재시도 가능 여부는 `errorCode` 로 구분한다.

분리 전에는 풀 스윕 표의 충돌 열을 만들 수 없었다. 충돌 횟수를 알려면 Redis `INCRBY` 호출 수를 세는 우회로가 필요했고, 지금은 응답으로 집계되며 그 값과 교차 확인된다.

## 딜을 만들어도 팔리지 않았다

측정을 처음 돌렸을 때 구매 2,099건이 전부 `400 TIME_DEAL_NOT_ACTIVE` 로 떨어졌다.

`TimeDeal.create()` 는 항상 `SCHEDULED` 를 만드는데, `ACTIVE` 로 바꾸는 코드가 리포지토리 어디에도 없었다. `isActiveAt()` 은 `status == ACTIVE` 를 요구한다. **API 로 만든 딜은 영원히 팔리지 않는 상태였다.** 이전 측정들은 SQL 로 상태를 직접 올려서 돌렸던 것이다.

고칠 때 갈림길이 있었다.

| | 전이 스케줄러만 추가 | 판단 주체를 시간으로 |
|---|---|---|
| 오픈 직후 | 스케줄러 주기만큼 못 산다 | 즉시 열린다 |
| 상태 라벨 | 정확 | 잠깐 늦을 수 있다 |
| 스케줄러가 죽으면 | 판매가 안 열린다 | 판매는 열린다 |

시간을 판단 주체로 뒀다. 스케줄러 주기만큼 생기는 창이 하필 **타임딜에서 가장 중요한 순간과 겹치기** 때문이다.

```kotlin
fun isActiveAt(now: Instant): Boolean =
    now in startAt..endAt && status != TimeDealStatus.SOLD_OUT && status != TimeDealStatus.ENDED
```

라벨은 `TimeDealStatusScheduler` 가 5초마다 뒤따라간다. 라벨이 필요한 이유는 판매 판단이 아니라 운영 가시성과 `findAllActive()` 같은 상태 기준 조회다. **판단과 라벨을 분리했으니 워커가 죽어도 판매는 열린다.**

대가는 `status` 컬럼이 최대 5초 동안 진실이 아니라는 것이다. `SCHEDULED` 인데 이미 팔리는 순간이 존재하므로, 운영 화면에서 상태만 보고 판단하면 안 된다.

측정 러너에서 `UPDATE time_deals SET status='ACTIVE'` 줄을 지웠고 그대로 돈다.

## 내린 결정과 대가

### Redis Lua 를 1차 필터로

`DECRBY` 단독으로는 "확인 후 차감"이 원자적이지 않다. GET → 판단 → DECRBY 사이에 끼어들면 재고가 음수가 된다. Lua 는 셋을 Redis 안에서 한 명령으로 끝낸다.

대가는 재고의 진실이 둘이 된다는 것이다. Redis 와 DB 가 어긋날 수 있고, 그래서 `StockReconciler` 가 필요해졌다. 부품 하나를 얻으려고 부품 하나를 더 만든 셈이다.

### 비관적 락 대신 Optimistic Lock

`SELECT FOR UPDATE` 는 같은 row 의 요청을 전부 줄 세운다. hot row 에서는 그 대기가 곧 커넥션 점유고, 풀 20개가 그대로 잠긴다. OL 은 잠그지 않고 UPDATE 시점에 version 으로 감지한다.

대가는 실패가 는다는 것. 다만 이 실패는 Oversell 이 아니라 기회 손실이다.

### 재시도 3회

Redis 를 통과한 소수가 같은 version 을 동시에 읽으면 1건만 성공한다. 재시도가 version 을 매번 새로 읽어서, 팔 수 있었는데 못 판 경우를 줄인다.

다만 이 경로는 정상 구성에서 한 번도 밟히지 않았다. Redis 가 앞에서 걸러 DB 에 도달한 100건이 서로 경합하지 않기 때문이다. 필터를 끈 대조군에서만 1,999건이 3회를 전부 소진했다.

무한 재시도는 그 자체가 부하라서 3회로 끊었다. 3이 최적이라는 근거는 없다. 측정해서 정한 게 아니라 일단 정한 값이다.

### StockReconciler 는 `SET` 이 아니라 `INCRBY`

크래시나 롤백 실패로 `Redis < DB` 가 생길 수 있어 60초마다 ACTIVE 딜을 돌며 복구한다. `SET` 으로 덮으면 복구하는 그 순간 진행 중이던 차감까지 지워버린다. 그래서 차분만 더한다.

### 이 설계를 안 쓸 조건

동시 요청이 재고 대비 크지 않으면 여기까지 갈 필요가 없다. 거부될 요청이 적으면 걸러낼 것도 없고, Redis 는 이득 없이 "두 번째 진실"이라는 비용만 남긴다. DB 단독 + OL 로 충분하다.

이 파이프라인이 값을 하는 건 거부될 요청이 통과할 요청보다 압도적으로 많을 때다. 그게 아니면 과한 설계가 맞다.

## 이번에 알게 된 것

**의도를 적어두면 나중에 어긋난 걸 찾을 수 있다.** 4월에 "실패 시 DB 에 접근하지 않는 게 핵심 목적" 이라고 주석을 남겼다. 8월에 재보니 요청 전량이 DB 를 두 번 치고 있었다. 주석이 없었으면 이 숫자를 보고도 "원래 이런 건가" 하고 넘어갔을 것이다. **어긋남은 기준이 있어야 보인다.**

**주석의 사정거리는 그 파일까지다.** `decrease()` 안에서는 정말로 DB 를 안 쳤다. 틀린 건 그 함수를 부르기 전에 이미 두 번 조회하던 호출자였다. 파일 단위로 맞는 것과 흐름 단위로 맞는 것은 다르다.

**주장을 검증하려면 대조군이 있어야 한다.** "Redis 가 자원을 지킨다" 는 Redis 를 켜고 재서는 확인되지 않는다. 재고 키를 크게 덮어 필터만 무력화하니 코드 한 줄 안 고치고 대조군이 만들어졌다.

**증상과 메커니즘은 다르다.** 조회가 느려진 건 봤지만 그게 풀 때문인지는 안 봤었다. `pending` 을 샘플링하고 나서야 대기열이 930까지 쌓이는 걸 확인했다. 그 전까지는 정황이었다.

**가장 강한 반론을 내가 먼저 재본다.** "풀만 늘리면 되지 않나" 는 이 설계에 대한 제일 자연스러운 공격이다. 재보니 4배 늘려도 60배 느렸고, 충돌은 오히려 4,978 에서 5,899 로 늘었다. 반론을 미리 재두면 그게 근거가 된다.

**측정을 돌리는 것 자체가 결함을 찾는 방법이다.** 첫 실행에서 구매 2,099건이 통째로 400 으로 떨어졌다. 부하를 재려다 "딜을 만들어도 팔리지 않는다" 는 걸 발견했다. **테스트 27건이 통과하는 상태였다.** 단위 테스트는 내가 물어본 것만 답한다.

**실패를 뭉뚱그리면 나중에 대가를 치른다.** 버전 충돌과 품절을 같은 예외로 던져서, 충돌 횟수를 알려면 Redis `INCRBY` 를 세는 우회로가 필요했다. 관측 가능성은 대시보드가 아니라 실패를 표현하는 타입에서 시작한다.

**측정 설계가 측정 결과보다 먼저다.** 한 점만 찍으면 그 점이 경계 어느 쪽인지 알 수 없다. 700 rps 에서 안 밀리길래 "효과가 없다" 고 적었는데, 유지 시간을 1초 늘리자 같은 요청률에서 꺾였다.

## 아직 못 밝힌 것

- **필터가 있을 때의 한계를 모른다.** 어느 풀 크기에서도 마르지 않아 경계를 못 찾았다. **"안 무너진다" 가 아니라 "이 규모에서는 안 무너진다"** 까지가 지금 말할 수 있는 전부다.
- **3,000 rps 이상을 못 잰다.** k6 와 애플리케이션이 같은 머신에서 돌아 측정기가 먼저 무너진다. 분리해야 한다.
- **재시도 3회가 적절한지 모른다.** 정상 구성에서 관측된 충돌은 1,500 rps 에서 2건뿐이다. 3은 측정으로 정한 값이 아니다.
- **경계의 정확한 위치.** 700~1,500 사이를 촘촘히 훑지 않았다.
- **Redis 앞에서 `findById` 를 한 번 친다.** 남은 0.11회의 대부분이 이것이다. 없애려면 딜 메타데이터를 캐시에 올려야 하는데 무효화 문제가 생긴다.
- **상태 라벨이 최대 5초 늦다.** 판매 판단에는 영향이 없지만 운영 화면에서 상태만 보면 안 된다.
- **Redis 가 죽으면 1차 필터가 사라진다.** 정합성은 DB OL 이 지키지만 자원 격리는 통째로 없어진다. 폴백은 없다.
- **단일 인스턴스 기준이다.** `StockReconciler` 와 `TimeDealStatusScheduler` 둘 다 인스턴스마다 도는 스케줄러라 중복 실행된다. 둘 다 멱등이지만 리더 선출이나 락이 필요하다.
- **테이블이 작아 쿼리 계획이 프로덕션과 다르다.** 이 부하로는 인덱스 설계가 검증되지 않는다.

## 구조

```
core/          도메인 — 모델, 판정 규칙, 포트. Spring·jOOQ·Redis 를 모른다
application/   유스케이스 — 트랜잭션 경계는 여기서만 연다
external/      어댑터 — 영속(jOOQ), 캐시(Redis Lua), 스케줄러, 웹
```

의존 방향은 `external → application → core` 단방향이다. `core/` 안에 Spring·jOOQ·Redis import 는 0건이라 `TimeDealValidator` · `StockDecreaser` · `StockRollbackHandler` 는 Spring Context 없이 단위 테스트가 돈다. 대신 `@Component` 를 못 붙여서 빈 등록은 `application/timedeal/config/TimeDealBeanConfig` 가 손으로 한다.

동시성 검증은 `PurchaseTimeDealConcurrencyTest` 가 Testcontainers 로 PostgreSQL·Redis 를 띄워서 돌린다.

## 측정 재현

```bash
docker compose up -d          # PostgreSQL(5437) · Redis(6378)
./gradlew build -x test
java -jar build/libs/ecommerce-0.0.1-SNAPSHOT.jar    # 기동 시 Flyway 가 스키마를 만든다

./scripts/run-timedeal-test.sh                       # 기본 구성
MODE=unfiltered ./scripts/run-timedeal-test.sh       # Redis 1차 필터 무력화 대조군
```

러너가 딜을 만들고 상태를 `ACTIVE` 로 올린 뒤 Redis·PostgreSQL 통계를 리셋하고 k6 를 돌린다. 상태를 올리는 단계가 필요한 건 `SCHEDULED → ACTIVE` 전이 경로가 없기 때문이다.

스크립트는 응답을 `201 / 409 / 5xx / 기타` 로 나눠 세고, 상품 조회 지연을 스파이크 전·중·후로 나눠 기록한다.

`generateJooq` 는 스키마가 있는 DB 를 향해야 한다. 갓 띄운 빈 DB 에 돌리면 생성 코드가 빈 껍데기로 덮여 컴파일이 깨진다. 생성 결과는 리포지토리에 커밋돼 있으니 스키마를 바꿀 때만 돌리면 된다.
