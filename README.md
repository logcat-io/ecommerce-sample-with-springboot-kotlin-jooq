# ecommerce-server — 타임딜 재고 차감

> 확정 실패할 요청을 DB 도달 전에 버려 커넥션 풀을 지키는 재고 차감 파이프라인.

Kotlin 2.2 / JDK 21 (Virtual Thread) / Spring Boot 4 / jOOQ 3.19 / PostgreSQL 16 / Redis 7 / k6

---

## 1. 무엇을 하려고 했나

동시성 제어가 필요하니 Redis 를 쓰자는 전제 아래 이미 구현되어 있던 서비스에서 일했다. 그 구조 위에 기능을 얹고 운영하면서 Redis 기반 락이 오히려 문제를 만드는 상황을 몇 번 겪었다. 같은 문제를 다시 만난다면 어떤 가정 위에서 DB 를 보호할까 — 그 질문에 답하려고 만든 코드다.

재고 100에 동시 2,000이 들어오면 1,900건은 확정 실패다. 재고를 열기도 전에 이미 정해져 있는 숫자다.

처음엔 이걸 "Oversell 을 어떻게 막느냐" 문제로 봤다. 그런데 그건 `UPDATE ... WHERE stock > 0` 한 줄로도 막힌다. 재고가 음수가 되는 일은 안 생긴다.

진짜 걸리는 건 다른 데 있다. 그 1,900건이 "너 실패야"라는 말을 듣기까지 **커넥션을 하나씩 붙들고 있다.** 풀은 20개다. 그동안 상품 조회도, 주문 내역도, 타임딜과 아무 상관 없는 요청까지 같은 줄에 선다. 타임딜 하나가 서비스 전체를 느리게 만든다.

그래서 이건 방어선을 쌓는 문제가 아니라 **어차피 실패할 요청에 얼마나 비싼 자원을 쓰느냐**의 문제라고 봤다. 층을 늘리는 대신 **거부 비용이 싼 곳에서 먼저 거부하는 쪽**으로 갔다.

## 2. 어떻게 했나

```
요청 ──→ [0차] Redis 재고 확인 (GET)          거부 비용: 메모리 읽기
           │ 재고 없음 → 409, DB 접근 0
           ▼
         [1차] 딜 조회 + 활성 검증              여기부터 DB
           ▼
         [2차] Redis Lua 원자 차감              원자적 판정
           │ 재고 부족 → 409
           ▼
         [3차] DB Optimistic Lock UPDATE
           │ version 불일치 → Redis 복구 + 409 (최대 3회 재시도)
           ▼
         [4차] UPSERT WHERE quantity + ? <= maxPerUser
           │ 1인 한도 초과 → Redis 복구 + 409
           ▼
         구매 확정
```

**0차가 이 설계의 전부다.** 확정 실패를 DB 앞에서 끊는다. 차감이 아니라 확인이라 실패해도 되돌릴 게 없고, 롤백 경로가 늘지 않는다.

원자적 판정은 2차의 Lua 가 한다. 0차를 통과했다가 2차에서 실패하는 요청이 존재하는데, 그건 결함이 아니라 필터의 성격이다. 0차는 게이트가 아니라 명백히 안 될 요청을 싸게 걷어내는 자리다.

세 층이 정합성을 겹쳐서 보장하는 구조가 아니다. 각 층이 서로 다른 실패를 맡는다.

| 층 | 막는 것 | 이게 없으면 |
|---|---|---|
| Redis Lua | 재고 소진 | 확정 실패가 DB 까지 온다 |
| DB OL | **Redis 와 DB 의 불일치** | Redis 가 재시작되면 초과 판매된다 |
| UPSERT WHERE | 1인 한도 | 한 사람이 여러 번 산다 |

특히 2층이 핵심이다. Redis 는 휘발성이고 DB 와 어긋날 수 있어서, Redis 만 믿으면 재시작 한 번에 Oversell 이 난다. DB OL 은 Redis 가 틀렸을 때의 최종 진실이다.

## 3. 결과 — 대조군과 함께 쟀다

전문은 [`reports/load-test-timedeal-spike.md`](reports/load-test-timedeal-spike.md) · 측정 기록은 [블로그](https://logcat-io.github.io/posts/redis-filter-db-reach-remeasured/).

처음 검증은 Oversell 만 봤다. 재고가 정확히 맞으니 끝났다고 봤는데, **그 측정에는 밀려나는 쪽이 아예 없었다.** 구매 요청만 쐈으니 §1 의 문제를 확인할 대상 자체가 없던 셈이다.

그래서 상품 조회를 전 구간 같이 흘리고, **필터만 무력화한 대조군**을 옆에 놓았다.

"Redis 가 자원을 지킨다"는 Redis 를 켜고 재서는 확인되지 않는다. 재고 키를 크게 덮어 1차 필터만 무력화하면 코드 한 줄 안 고치고 대조군이 된다. DB 가 유일한 거부 주체가 되는 구성이다.

재고 100, 구매 요청 6,000건(피크 1,500 rps · 3초), 상품 조회 50 rps 를 전 구간 흘렸다. 조회를 같이 흘린 이유는 이 설계의 주장이 "무관한 요청이 밀린다"이므로 **밀려나는 쪽을 재야 하기 때문**이다.

### DB 도달

| | 필터 OFF | 필터 ON |
|---|---:|---:|
| `time_deals` 스캔 / 요청 | 6.13 ~ 7.58 | **0.08 ~ 0.11** |
| `time_deal_purchases` 스캔 / 요청 | 0.02 | **0.02** |
| 합계 | 약 6.8회 | **0.11회** |

요청 6,000건 중 DB 까지 온 것은 500~680건이다. 재고 100 에 대해 그보다 큰 이유는 **재고가 마르는 동안 도착한 요청들이 0차를 통과하기 때문**이다. 요청 수 기준으로는 9%.

### 구매 경로

| | 필터 OFF | 필터 ON |
|---|---:|---:|
| p95 | 144 ~ 203 ms | **0.89 ~ 0.98 ms** |

### 3-1. 커넥션 풀이 실제로 마르는가

조회가 느려진 것만으로는 원인을 말할 수 없다. 풀 크기를 바꿔가며 스파이크 동안 `hikaricp.connections.pending` 을 200ms 간격으로 샘플링했다. 1,500 rps 고정.

| 풀 | | 조회 p95 | active 최대 | **pending 최대** | 충돌 |
|---:|---|---:|---:|---:|---:|
| **10** | ON | 2.1 ms | 1 / 10 | **0** | 0 |
| | OFF | 869 ms | 10 / 10 | **930** | 4,978 |
| **20** | ON | 2.7 ms | 7 / 20 | **0** | 0 |
| | OFF | 323 ms | 20 / 20 | **370** | 5,574 |
| **40** | ON | 2.4 ms | 3 / 40 | **0** | 0 |
| | OFF | 140 ms | 40 / 40 | **267** | 5,899 |

대조군은 모든 풀 크기에서 100% 포화되고 대기열이 930까지 쌓인다. 필터가 있으면 어느 크기에서도 마르지 않는다 — 최대 7개를 썼다.

추론이 아니라 관측이다.

### 3-2. 풀만 늘리면 되지 않나

이 설계에 대한 가장 자연스러운 반론이라 직접 쟀다. 10에서 40으로 4배 늘리자 869ms 가 140ms 로 **6배 개선됐다. 완화는 된다.**

그런데 같은 조건에서 필터가 있는 쪽은 2.4ms 다. 그리고 PostgreSQL 은 커넥션마다 백엔드 프로세스를 띄우고, 그 비용은 인스턴스 수만큼 곱해진다.

더 중요한 건 충돌 쪽이다.

```
pool 10 → 4,978
pool 20 → 5,574
pool 40 → 5,899     사실상 전량
```

**풀을 키울수록 버전 충돌이 늘었다.** 커넥션을 더 주면 같은 row 를 동시에 때리는 요청이 늘고, 충돌이 늘면 재시도가 늘고, 재시도가 늘면 왕복이 는다. 늘린 자원의 일부가 경합 증폭으로 되돌아온다.

위 절대 수치는 이 머신에서 나온 값이라 다른 환경에서 재현되지 않는다. 규모와 무관하게 남는 결론은 하나다 — 풀 확대는 선형으로 먹히지 않는다.

### 3-3. 언제 값을 하고 언제 안 하나

조회 p95, 스파이크 중 기준.

| 피크 | 필터 ON | 필터 OFF |
|---:|---:|---:|
| 700 rps | 2.0 ~ 3.0 ms | 2.7 ~ 11.0 ms |
| **1,500 rps** | **2.4 ~ 3.2 ms** | **131 ~ 191 ms** |
| 3,000 rps | 편차 20배 | 1,613 ~ 2,122 ms |

700 rps 아래에서는 두 구성이 사실상 같다. 거부될 요청이 풀을 경합시킬 만큼 많지 않다. 이 구간에서 Redis 는 이득 없이 "재고의 두 번째 진실"이라는 비용만 남긴다. **이 설계를 안 써도 되는 조건이 여기다.**

3,000 rps 는 결론에서 뺐다. 양쪽 다 무너지고 필터 ON 의 편차가 20배다. k6 와 애플리케이션이 같은 머신에서 CPU 를 나눠 쓰는 한계라 이 구간 숫자로는 아무 말도 하지 않는다.

정합성은 전 구간에서 유지됐다. 3,000 rps · 필터 OFF 로 12,000 요청을 몰아도 성공은 정확히 100건, 5xx 는 0이다.

## 4. 내린 결정과 대가

### Redis 재고 확인을 호출 맨 앞에

`findById` 나 한도 조회보다 앞에 둔다. 확정 실패가 DB 를 건드리지 않게 하려면 다른 자리가 없다.

**대가:** 확인과 실제 차감 사이에 다른 요청이 끼어들 수 있다. 정확성은 2차 Lua 가 잡으므로 문제가 안 되지만, 통과했다가 뒤에서 실패하는 요청이 생긴다.

### 1인 한도는 UPSERT 하나로 닫는다

`ON CONFLICT DO UPDATE ... WHERE quantity + ? <= maxPerUser` 가 원자적으로 check-and-increment 를 수행한다. 앞단에 `SELECT` 로 선검사를 두면 **모든 요청**이 DB 를 한 번 더 치는 대가로 재구매자 한 명의 롤백을 아낀다. 그 거래를 하지 않는다.

같은 사용자가 동시에 20회 시도해도 정확히 1건만 성공하는 것을 통합 테스트로 확인했다.

### 비관적 락이 아니라 Optimistic Lock

`SELECT FOR UPDATE` 는 같은 row 의 요청을 전부 줄 세운다. hot row 에서는 그 대기가 곧 커넥션 점유고, 풀이 그대로 잠긴다. OL 은 잠그지 않고 UPDATE 시점에 version 으로 감지한다.

**대가:** 실패가 는다. 다만 이 실패는 Oversell 이 아니라 기회 손실이다.

### 재시도 3회

Redis 를 통과한 소수가 같은 version 을 동시에 읽으면 1건만 성공한다. 재시도가 version 을 매번 새로 읽어서, 팔 수 있었는데 못 판 경우를 줄인다.

**3이 최적이라는 근거는 없다.** 측정해서 정한 게 아니라 일단 정한 값이다. 그리고 정상 구성에서는 이 경로가 거의 안 밟힌다 — 1,500 rps 에서 2건 관측됐다.

### 판매 가능 여부는 시간이 정한다

```kotlin
fun isActiveAt(now: Instant): Boolean =
    now in startAt..endAt && status != TimeDealStatus.SOLD_OUT && status != TimeDealStatus.ENDED
```

상태 라벨(`SCHEDULED → ACTIVE`)은 5초 주기 워커가 뒤따라간다. 라벨을 판단 주체로 삼으면 워커 주기만큼 **"시작 시각은 지났는데 못 사는" 창**이 생기는데, 그 창이 하필 타임딜에서 가장 중요한 순간과 겹친다.

**대가:** `status` 컬럼이 최대 5초 동안 진실이 아니다. 운영 화면에서 상태만 보고 판단하면 안 된다.
**얻는 것:** 워커가 죽어도 오픈 시각에 판매는 열린다.

### 실패를 예외가 아니라 값으로 돌려준다

```kotlin
sealed class Result {
    object Success : Result()
    object StockExhausted : Result()
    data class VersionConflict(val attempts: Int) : Result()
}
```

**예외로 던지면 호출자가 뭉갤 수 있다.** `catch (e: Exception)` 한 줄이면 세 가지 실패가 한 덩어리가 되고, 새 실패 케이스를 추가해도 컴파일러는 아무 말도 안 한다. 빠뜨린 걸 배포하고 나서야 안다.

값으로 돌려주면 호출자가 반드시 마주 본다. Go 에서 `error` 를 반환값으로 다루는 것과 같은 방향이고, Kotlin 에서는 `sealed` + `when` 이 그걸 **컴파일러가 강제**하게 만든다. 분기를 하나라도 빼면 컴파일이 안 된다.

그래서 얻는 것 — 결과마다 다른 응답을 빠뜨릴 수 없다.

| Result | 응답 | 클라이언트가 할 일 |
|---|---|---|
| `Success` | `201` | — |
| `StockExhausted` | `409 STOCK_EXHAUSTED` | 재시도해도 의미 없음 |
| `VersionConflict(attempts)` | `409 STOCK_VERSION_CONFLICT` | 재시도하면 성공할 수 있음 |

같은 409 인데 뒤엣것은 재고가 남아 있는 실패다. 둘을 한 예외로 던지면 클라이언트가 정반대로 행동하고, 로그에서도 "품절이 많았다"와 "경합이 심했다"를 못 가른다.

부수적으로 관측도 열린다. 이 분리가 없으면 위 풀 스윕 표의 충돌 열을 만들 수 없다 — 충돌 횟수를 알려면 Redis `INCRBY` 호출 수를 세는 우회로가 필요했다.

**대가:** 실패 케이스가 늘 때마다 `when` 분기와 예외 매핑을 같이 고쳐야 한다. 컴파일러가 알려주니 빠뜨리진 않지만, 손댈 곳은 는다.

### 복구는 `SET` 이 아니라 `INCRBY`

크래시나 롤백 실패로 `Redis < DB` 가 생길 수 있어 60초마다 ACTIVE 딜을 돌며 복구한다. 이때 `SET` 으로 정답을 덮고 싶어지는데, 그러면 안 된다.

`SET` 은 read-modify-write 가 애플리케이션에 걸쳐 있다. 현재 값을 읽고 → 얼마를 넣을지 계산하고 → 쓰는 세 단계인데, 그 사이에 구매 요청이 `DECRBY` 를 하면 **그 차감이 통째로 사라진다.** 복구하려다 이미 팔린 재고를 되살리는 셈이다.

`INCRBY` 는 Redis 단일 명령이라 계산과 쓰기가 서버 안에서 원자적으로 끝난다. 차분만 더하므로 복구 작업이 진행 중인 트래픽과 경합하지 않는다.

**그래서 얻는 것:** 복구를 트래픽이 멈춘 뒤로 미룰 필요가 없다. 언제 돌려도 안전하다.

"정답으로 덮는다"가 직관적인데 동시성 아래에서는 **차분을 더하는 쪽이 안전하다** — 같은 이유로 재고 차감도 Lua 안에서 `DECRBY` 로 한다.

## 5. 놓친 것

측정으로 답을 얻은 만큼 답을 못 얻은 것도 분명해졌다. 이 설계의 사정거리를 적어 둔다.

**필터가 있을 때의 한계를 못 찾았다.** 어느 풀 크기에서도 마르지 않아 경계가 어디인지 확인하지 못했다. 이건 "안 무너진다"가 아니라 **"이 규모에서는 안 무너진다"**로만 말할 수 있다는 뜻이다.

**측정 환경이 먼저 무너진다.** k6 와 애플리케이션이 같은 머신에서 CPU 를 나눠 써서 3,000 rps 이상을 못 잰다. 이 구간 숫자로는 아무 말도 하지 않았다.

**절대 수치는 이식되지 않는다.** 869ms·930 같은 값은 이 머신 고유다. 다른 환경으로 옮겨지는 건 "풀 확대는 경합 증폭 때문에 선형이 아니다"라는 모양이지 숫자가 아니다.

**단위 테스트가 답하지 않는 영역이 있다.** 테스트 44건이 통과해도 부하를 걸어야 보이는 것들이 따로 있었다. 상태 전이가 판매 판정을 막는 구조도 부하 시나리오를 돌리다 나왔다.

### 5-1. 남겨둔 항목

- **재시도 3회가 적절한지 모른다.** 정상 구성에서 관측된 충돌이 1,500 rps 에서 2건뿐이라 표본이 부족하다. 3은 측정으로 정한 값이 아니다
- **경계의 정확한 위치.** 700~1,500 사이를 촘촘히 훑지 않았다
- 0차 뒤의 `findById` 는 남아 있다. DB 도달 0.11회의 대부분이 이것이다. 없애려면 딜 메타데이터를 캐시에 올려야 하는데 무효화 문제가 새로 생긴다
- Redis 가 죽으면 0차·2차가 사라진다. 정합성은 DB OL 이 지키지만 자원 격리는 통째로 없어진다. 폴백은 없다
- **단일 인스턴스 기준이다.** `StockReconciler` 와 상태 전이 워커 둘 다 인스턴스마다 도는 스케줄러라 중복 실행된다. 둘 다 멱등이지만 리더 선출이나 락이 필요하다
- 테이블이 작아 쿼리 계획이 프로덕션과 다르다. 이 부하로는 인덱스 설계가 검증되지 않는다

## 6. 구조

```
core/          도메인 — 모델, 판정 규칙, 포트. Spring·jOOQ·Redis 를 모른다
application/   유스케이스 — 트랜잭션 경계는 여기서만 연다
external/      어댑터 — 영속(jOOQ), 캐시(Redis Lua), 스케줄러, 웹
```

의존 방향은 `external → application → core` 단방향이다. `core/` 안에 Spring·jOOQ·Redis import 는 0건이라 `TimeDealValidator` · `StockDecreaser` · `StockRollbackHandler` 는 Spring Context 없이 단위 테스트가 돈다. 대신 `@Component` 를 못 붙여서 빈 등록은 `application/timedeal/config/TimeDealBeanConfig` 가 손으로 한다.

동시성 검증은 `PurchaseTimeDealConcurrencyTest` 가 Testcontainers 로 PostgreSQL·Redis 를 띄워서 돌린다. 테스트 44건.

### 측정 하네스에 대해

시나리오 파라미터(초과청약 배수·도착 형태·경쟁 트래픽)와 결과 해석은 직접 정했고, k6 하네스 작성과 반복 실행·수치 정리는 Claude 에게 맡겼다. "재고 키를 덮어 필터만 무력화한다"는 대조군 구현 방법은 Claude 제안이고, 채택 여부와 어느 구간을 결과에 쓸지는 직접 판단했다. 3,000 rps 구간은 측정기가 먼저 무너져 편차가 20배라 결과에서 뺐다.

러너가 매 실행 전 데이터를 초기화하고(`TRUNCATE` + `FLUSHDB`) 통계를 리셋한다. 런마다 행이 쌓이면 조회 비용이 달라져 런끼리 비교가 안 된다.

`generateJooq` 는 스키마가 있는 DB 를 향해야 한다. 갓 띄운 빈 DB 에 돌리면 생성 코드가 빈 껍데기로 덮여 컴파일이 깨진다. 생성 결과는 커밋돼 있으니 스키마를 바꿀 때만 돌리면 된다.
